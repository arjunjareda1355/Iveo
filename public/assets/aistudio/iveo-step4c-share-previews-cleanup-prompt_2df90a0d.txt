6. KNOWN LIMITS OF 4C (PLAN FOR THEM)
- Chat apps and social sites cache previews, sometimes for days. The image address changes whenever your name, bio, photo or vibe change, which helps, but some apps ignore that. Their debugger tools force a refresh.
- The generated image uses the Noto Sans font (included by default). Names written in non-Latin scripts (Arabic, Chinese, Japanese, Hindi and so on) cannot be drawn in it, so the card shows the @username instead of the name. Custom fonts can be added later. Emoji in names may not draw either.

- The webhook is eventually consistent: renames and deletions can take up to a minute (Clerk retries failed deliveries). The in-app sync from Step 3 stays as a backup.
- Deleting data is not one atomic transaction. If something fails halfway the webhook retries; in rare cases a stray storage file can remain.
- There is still no full Content-Security-Policy. It needs careful testing with Clerk, YouTube, Spotify and SoundCloud and is a later task.

-- 1. AVATARS MAY ONLY COME FROM CLERK'S IMAGE HOST -------------------------
-- (The share-card image function fetches avatars, so the address must be
-- limited to a trusted host.) Existing values that do not match are cleared;
-- the app refills them from Clerk on the next visit.
update public.profiles
set avatar_url = null
where avatar_url is not null
  and avatar_url !~ '^https://(img\.clerk\.com|images\.clerk\.dev)/';

alter table public.profiles drop constraint if exists profiles_avatar_url_ok;
alter table public.profiles
  add constraint profiles_avatar_url_ok check (
    avatar_url is null or (
      char_length(avatar_url) <= 2048
      and avatar_url ~ '^https://(img\.clerk\.com|images\.clerk\.dev)/'
    )
  );

-- 2. MORE RESERVED USERNAMES ---------------------------------------------------

  ('iveo'), ('ivio'), ('clerk'), ('webhook'), ('webhooks'), ('vercel'), ('supabase')
on conflict (username) do nothing;

5. api/page.ts: SERVER-RENDERED METADATA
=====================================================================
Purpose: every request for a single-segment path like /maya (and for private routes like /dashboard) is answered with the SAME app shell (the built index.html) with the correct <head> tags injected. The browser then loads the normal app, which renders the page. Search engines, chat apps and social sites read the tags.

5.1 Request and routing
- Export both GET and HEAD handlers; any other method returns 405 with an Allow header.
- Read the path segment from the query parameter "u" (set by the rewrite in Section 8). Run classifySegment on it.
- The shell template: first try to read dist/index.html from the filesystem (it is bundled with the function through includeFiles in Section 8; resolve it with path.join(process.cwd(), "dist", "index.html") using node:fs/promises); if that fails, fetch `${origin}/index.html` with the timeout from 2.6; if that also fails, return a minimal HTML document with a <noscript> note and a meta refresh to the origin with status 200 and Cache-Control "no-store".

5.2 Cases
- "username": call loadPublicPage. If it returns a page: found case (5.3). If it returns null (unknown, unpublished or not set up): generic case with robots "noindex".
- "private": generic case with robots "noindex, nofollow" and the title "<Route label> | iveo" where the label is Log in, Create your account, Dashboard, Welcome, Account for login, signup, dashboard, onboarding, account.
- "info" and "reserved" and "invalid": generic case with the default title and robots "index, follow" for info routes, "noindex" for the others.
Generic case tags: title "iveo: one link for everything you make"; description "iveo gives you one calm, customizable page for all your links. Claim your name, pick a vibe and share it anywhere. Free to start."; canonical = origin + "/" for info routes, none for noindex cases; og:type website; og:site_name iveo; og:title (same as title); og:description; og:url; og:image = ogImageAddress(origin) with width 1200, height 630, type image/png, alt "iveo: one link for everything you make"; twitter:card summary_large_image with twitter:title, twitter:description, twitter:image.
Use the brand text exactly as in these strings. Keep them in api/_lib so the client copy (src) is not imported.

5.3 Found case tags
- name = displayName if non-empty, otherwise "@" + username. Title = truncate(name, 60) + " | iveo".
- description = truncate(bio, 160) when a bio exists, otherwise "Links by @<username> on iveo."
- canonical = pageAddress(origin, username) (lowercase).
- robots: "noindex, nofollow" when hideFromSearch, otherwise "index, follow".
- og:type "profile"; og:site_name "iveo"; og:title (the name); og:description; og:url (canonical); og:image = ogImageAddress(origin, username, version(page)) with og:image:width 1200, og:image:height 630, og:image:type image/png, og:image:alt "<name>'s page on iveo"; profile:username (the username, no "@"); twitter:card summary_large_image, twitter:title, twitter:description, twitter:image (same image).
- JSON-LD (safeJsonLd): { "@context": "https://schema.org", "@type": "ProfilePage", "mainEntity": { "@type": "Person", "name": <name>, "alternateName": "@<username>", "url": <canonical>, "description": <bio, only when present>, "image": <avatarUrl, only when present> } }.
- Every dynamic value goes through escapeHtml for attributes and text; JSON-LD through safeJsonLd.

5.4 Response
- Status 200, Content-Type "text/html; charset=utf-8".
- Found case: Cache-Control "public, s-maxage=60, stale-while-revalidate=600". Generic cases from a successful shell read: "public, s-maxage=300, stale-while-revalidate=3600". If Supabase failed or the shell fell back: "no-store".
- Never include user text in headers. Never echo the query string.
- HEAD returns the same headers without a body.

5.5 Failure behavior
Every failure falls back to the generic case (never a 500, never a blank page). A Supabase timeout must not delay the response beyond about 3 seconds in total.

7. api/clerk-webhook.ts: KEEPING THE DATABASE IN STEP WITH CLERK
=====================================================================
7.1 Request handling
- Only POST is accepted (anything else: 405 with an Allow header).
- Verify the signature BEFORE reading anything else: first choice verifyWebhook(request, { signingSecret }) imported from "@clerk/backend/webhooks" (signingSecret from env). If that function does not exist in the installed version, use "svix": new Webhook(secret).verify(rawBody, { "svix-id", "svix-timestamp", "svix-signature" headers }). Read the raw body only once.
- Invalid or missing signature: 400 with { "error": "invalid_signature" }. Missing configuration: 500 with { "error": "not_configured" }.
- Only two event types are handled: "user.deleted" and "user.updated". Any other verified event: 200 with { "ok": true, "ignored": true }.
- The Clerk user id is event.data.id and must match /^user_[A-Za-z0-9]+$/; otherwise 200 ignored (log the code "bad_user_id" only).
- Respond within a few seconds; keep the work small. Return 200 { "ok": true } on success or on harmless conflicts, and 500 { "error": "temporary" } on transient failures (network, 5xx from Supabase) so that Clerk retries.

7.2 user.deleted
1. Delete the person's images: using adminClient().storage.from("link-images"), list the folder named after the user id (list(userId, { limit: 1000 })), remove the listed paths (userId + "/" + name), and repeat until the list is empty (at most 20 rounds). Failures here return 500 (so the event is retried) unless the folder simply does not exist.
2. Delete the profile row: adminClient().from("profiles").delete().eq("user_id", userId). This also removes links and analytics rows through cascades. Deleting zero rows is a success (it makes the handler idempotent).
3. Return 200.

7.3 user.updated
- Read data.username (string or null) and data.image_url (string or null).
- Build a patch: username = normalizeUsername(data.username) when valid (it must also not be in RESERVED); avatar_url = data.image_url when it matches the allowed Clerk hosts, otherwise unchanged.
- If the patch is empty: 200 ignored.
- Apply it with adminClient().from("profiles").update(patch).eq("user_id", userId) (no insert: if the person has no profile row yet, nothing is updated and that is fine).
- On a unique violation for username (error code 23505) or a reserved-name error (message "username_reserved"): do NOT retry. Apply only the avatar part if present, return 200, and log the code "username_conflict". The in-app sync from Step 3 will send the person to choose another name the next time they open the dashboard.
- On other errors return 500.

7.4 Safety
- No other table is touched. No plan changes. No reads of other people's data. No user text is logged.
- The function never returns data from the database.
